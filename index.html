TruSales · Greenfield build

A CRM built from scratch, agent-first

Replacing a licensed CRM and its data-enrichment stack with an in-house platform — a React front end and a Node back end — inside a single quarter, with agents as the primary implementation surface rather than autocomplete.

Type GreenfieldStack React · NodeWindow May–Aug 2026Services 2
17 weekscalendar time, start to working platform
~160Klines of application code across two services
5,239unit and integration tests passing
1.1–1.2xrewrite ratio — output survived rather than churned
01 · The challenge

Replace the licence, keep the rigour

Buying a CRM meant paying for a licence and a separate enrichment stack, and still bending the sales process to fit someone else’s model. Building one meant owning the process — and owning the risk that an agent-built codebase quietly rots.

Two products, one quarter

A React front end and a Node back end, both greenfield, both expected to reach production quality in the same window a procurement cycle usually takes.

Agents doing the writing

Not inline suggestions — agents as the surface where the implementation actually happens, which changes what the team has to supervise.

The question nobody had answered

Can a team keep an agent-built codebase honest for four months? Velocity is easy to demonstrate in week one and much harder to defend in week fourteen.

No licence to fall back on

Replacing a working commercial tool means the replacement has to be genuinely finished, not a promising prototype.

02 · How we ran it

Make the agents accountable to something

The method was built around a simple principle: every claim the system makes about itself has to be verifiable by a script, not by a person reading a summary.

01
Rules the agents load themselves

Conventions live in files the agents read at the start of every session, with a stated precedence order so conflicts resolve the same way every time — rather than living in a prompt that drifts.

02
Specs before code

34 technical specs and 69 capability specs written before implementation. The spec is what the agent is held to, and what the reviewer checks against.

03
A ledger only a script can mark green

Capabilities are tracked in a ledger where nothing can be marked verified by hand. When it was first enforced it exposed 14 rows marked “passing” whose tests had never actually run.

04
Generate the boring half

Routes and access rules are generated from one file describing 50 entities, so the surface area most likely to drift is derived rather than typed.

05
Gate drift in CI

Checksum drift gates sit behind an eight-stage pipeline, so a generated file edited by hand fails the build instead of silently diverging.

A ledger nobody can mark green by hand turns “it works” from an opinion into a check you can run.

The method, in one line
03 · What it delivered

Output that survived the quarter

The numbers that matter here are not just how much was produced, but how much of it was still standing at the end.

160K lines, two services, 17 weeks

A complete front end and back end, counted from git rather than estimated.

5,239 tests passing

4,043 on the front end and 1,196 on the back end — unit and integration, running in CI.

22 of 46 capabilities script-verified green

The ledger reports what is actually proven, not what someone believed was done.

Rewrite ratio 1.19x and 1.09x

Close to one pass per line: the work was largely written once and kept, rather than regenerated repeatedly.

~USD 15 per agent session

A list-price estimate from a 13-session sample of front-end telemetry — small against the licence it replaced.

A method that outlives the project

The rules, ledger and drift gates are project-agnostic; the next build starts with them already in place.

Figures counted from git and the front-end capability ledger. Tests are unit and integration. Cost is a list-price estimate derived from front-end session telemetry across a 13-session sample.

TruIAM · Brownfield refactor

Three identity services rebuilt, nothing downstream changed

Rebuilding the identity, database and identity-provider services on a new managed identity service — with every endpoint keeping its exact request and response, so the front end needed no change at all.

Type BrownfieldServices 3Front-end changes 0Validation Automated
3microservices rebuilt as drop-in replacements
0production incidents during the migration
99endpoints parity-checked automatically
9.5 hoursto design and stand up the method
01 · The challenge

Change the engine without touching the wheel

Identity is the one service where a quiet failure is worst: nothing crashes, people simply get access they shouldn’t have, or lose access they need. The migration had to be provably identical, not apparently identical.

A hard contract

Every endpoint had to keep its exact request and response shape. Not equivalent — identical, field for field, so no downstream team had to be involved.

Silent failure as the main risk

A broken auth path announces itself. A subtly wrong permission payload does not, and may not surface for weeks.

Three services, one deadline

Identity, database and identity-provider services all moving onto a new managed identity service, each with its own surface.

“Looks good to me” was not an option

Manual sign-off across 99 endpoints is both slow and unreliable — exactly the kind of review that misses the one field that changed.

02 · How we ran it

Build the referee before the work

Rather than migrating and then testing, the team built a parity harness first, and let it be the thing that decided whether each service was done.

01
Preflight, then four phases

Discover, static diff, runtime diff, report. Each phase has to pass before the next one is worth running.

02
The harness owns the judgement

Every call, every diff and every classification rule lives in the harness. Agents own the fixtures and the report — never the pass/fail decision itself.

03
Specs from the running service

Live specifications are fetched from the service as it actually runs, not read from the repository, so the comparison is against reality rather than intent.

04
One real session, replayed

A genuine browser run was captured once and then replayed against both the old and new back ends, so the comparison covers real sequences rather than synthetic calls.

05
Humans gate the destructive calls

Endpoints that delete or revoke are flagged and reviewed by a person before any run touches them.

The harness decides, not the reviewer. That is the whole reason there were no incidents.

Why it held
03 · What it delivered

A migration nobody noticed

The best outcome for an identity refactor is that no one outside the team has a story about it. That is what happened.

Zero production incidents

Across all three services, through the full migration.

99 endpoints catalogued and checked

Every one compared automatically for parity, with destructive calls flagged for human review first.

100% automated validation

No manual sign-offs. Every claim of parity is a check that can be re-run on demand.

Zero front-end work

The contract held, so no downstream team had to schedule anything.

One harness, three services, no code changes

The same harness was reused across all three — configuration, not new code.

Reusable on the next refactor

The harness is generic by design. The next migration starts with the referee already built.

Figures taken from the migration records. The parity harness is generic by design: the next refactor needs configuration, not new code.

Background verification provider · AI-SDLC readiness

Measuring whether AI was actually helping

A global background-screening and credential-verification provider had AI tools in daily engineering use across regulated, multi-country markets — and no way to tell whether they were improving quality or just changing how the work felt.

Type Advisory studySector Regulated screeningAccess Read-onlyOutput Roadmap + ROI
222defects traced to where they entered and were found
221 of 222would have been caught earlier by the recommended agents
26agents proven by defect evidence, of ~40 recommended
6.5–22xmodelled annual return on the cost of adoption
01 · The challenge

Adoption without evidence

The tools were already in people’s hands. What was missing was any objective read on whether they were helping — and in a regulated market, “it feels faster” is not a defensible basis for scaling.

AI already in daily use

This was not a question of whether to start. Engineers were using AI tools every day; nobody could say what it had changed.

No baseline to compare against

Without knowing where defects currently enter and where they are caught, any claim of improvement is unfalsifiable.

Regulated, multi-country delivery

Screening and credential verification carry real compliance weight. A change to how software is built has to be defensible to an auditor, not just to a sprint review.

A path, not a pilot deck

The ask was an objective current-state view and a safe, practical adoption path — something the engineering organisation could actually act on.

02 · How we ran it

Read the evidence that already existed

No surveys and no instrumentation project. The study used the organisation’s own history — its tracker, its wiki, its repositories — read only, and traced what actually happened.

01
Map the real lifecycle

Every client stage mapped onto a six-phase lifecycle aligned to PMI, so the analysis describes how the organisation genuinely works rather than an idealised process.

02
Read-only analysis

The work tracker, the wiki and the code repositories, examined without changing anything or asking teams to adopt new tooling for the duration.

03
Trace real work, defect by defect

3 real work items and 222 defects across 3 releases, each traced to the phase where it entered and the phase where it was caught.

04
Design the flow on their own tools

An agentic delivery flow built on the stack already in place, so adoption is a change of practice rather than a migration.

05
Model the return on their own data

An ROI model built from the client’s historical defect data, not from vendor benchmarks or industry averages.

221 of the 222 defects we traced would have been caught earlier. That is an argument, not an impression.

What the evidence showed
03 · What it delivered

A baseline, a shortlist and a first step

The study produced something the organisation did not have before: a defensible picture of its own delivery, and a sequenced way to improve it.

The first measured baseline

Where defects are caught today, across roughly 13,900 defects a year.

A quick win sitting in plain sight

Most code changes were skipping quality checks entirely — fixable by configuration, before any AI adoption at all.

26 agents proven against real defects

Of roughly 40 recommended, 26 were validated against defects that actually occurred rather than hypothesised use cases.

221 of 222 caught earlier

The modelled effect of the recommended agents on the traced defect set.

A phased roadmap starting small

Beginning with a one-pod pilot, so the model is validated at low cost before it is scaled.

A method they can repeat

The same analysis can be re-run against every release, turning a one-off study into a standing measure.

Agent impact and ROI are modelled from the client’s historical data; a pilot validates them before scaling. The client is unnamed at their request.
